# 问题分析方法论 Skill

系统化的问题根因分析方法论。当遇到 bug、异常行为、结果与预期不符、"为什么不工作"、需要调试定位根因，或发现自己陷入"反复假设-修改-失败"循环时，强制遵循"证据优先、追完整数据流、一次一变量、先查自己代码再怀疑外部"的纪律，杜绝盲猜。

---

## 概述

此 Skill 是一个**纪律清单**，强制在分析问题时严谨，避免"假设 → 改 → 失败"的盲猜循环。当你在调试、定位根因、或发现自己开始反复猜测时，**停下来**按这个流程走。

它来自两起真实教训：一起是调试"CLI 路径 LLM 工具调用失败"时连续 6 个错误假设全失败（见「典型教训」），固化出"证据优先、追完整数据流"的定位纪律；另一起是 2026-11-21 幻影通告 bug——存在 12 天、被四层机制层层遮蔽才暴露——固化出「遮蔽类 bug」专节的发现与防复发纪律。

### 适用场景

- bug、异常行为、结果与预期不符
- "为什么不工作"、"为什么 X 行为和 Y 不一样"
- 调试、定位根因
- 对比"工作的路径 vs 失败的路径"找差异
- **发现自己已经在反复假设时**（这是最该停下、改用这个 Skill 的信号）
- **"这个问题为什么这么久才发现"类复盘**（遮蔽类 bug，见下方专节）

## 核心纪律（必须遵守）

### 1. 证据分级：推断 ≠ 结论

- 下"根因是 X"之前，必须有**直接、完整**的证据支撑。
- 如果只是推断，明确说"我怀疑 X，但还没验证"，**绝不斩钉截铁地下结论**。
- 警惕"模型 / 服务 / 第三方"这类你没法直接验证的归因——放到**最后**怀疑。

### 2. 追完整数据流，不中间归因

- 从输入到**最终实际输出**，每一层都确认字段对得上。
- **先搞清楚日志 / 证据记录的是哪一层**——绝不能假设"日志 = 完整请求 / 完整数据"。
  日志常常是中间层（如应用层 event，不是真正发出去的 HTTP body / 实际执行输入），
  会缺关键字段。在不完整的证据上反复对比，永远找不到根因。
- 找不到根因时，先反思："我是不是在错误的层打转？真正的证据在哪一层？我抓到的
  是'准备的数据'还是'真正用出去的数据'？"

### 3. "只一个路径失败" = 该路径特有的代码问题

- 如果 A 路径工作、B 路径失败，**第一怀疑对象是 B 路径特有的代码**
  （adapter、包装层、该路径独有的配置 / 转换），**不是**共性问题（模型、共享函数、
  共享配置）。
- 共性的东西在 A 能工作，就基本排除了——别再怀疑它。

### 4. 一次只改一个变量

- 最小改动 → 验证 → 再下一步。
- **绝不**同时改多个（system prompt + 配置 + 代码 + 参数），否则一个变量生效 / 失效
  你都分不清，永远定位不了。

### 5. 怀疑自己的代码，先于怀疑外部

- 先把自己能控制的每一层代码确认对（输入到输出的每一跳），再怀疑模型 / 服务 / 第三方。
- 尤其"模型不调工具""服务返回怪格式"这种归因，几乎总是自己中间某层把数据弄丢了
  或弄错了，而不是模型 / 服务的问题。

### 6. 不给自己找台阶

- "日志没记这个字段""可能是模型的问题""这个不好验证"——这些话一出现，
  立即转成"为什么没记？怎么直接验证？我能在哪一层抓到真数据？"，
  而不是绕过去、换个假设继续猜。

## 标准流程

1. **抓最终实际输出**：先看真正发出去 / 执行的数据（HTTP body、实际传给下游的参数、
   实际落盘的结果），不是中间层日志。明确确认：我手里的证据是哪一层？
2. **对比工作 vs 失败**：找一条**确定工作**的路径，和失败的路径**逐层、逐字段**
   对比完整数据（包括日志没记的字段——用临时打印 / eprintln / 断点抓）。
3. **定位分歧点**：从哪一层开始两边不一样？分歧点 = 嫌疑根因。
4. **最小验证**：在分歧点做**最小、单一**改动，验证假设。
5. **确认或回退**：验证通过 = 根因确认，修复；不通过 = 回到第 1 步，反思是不是
   看错了层、抓错了证据。

## 反模式（必须避免）

- ❌ 反复"假设 → 改 → 失败"循环，每次都没充分验证就下斩钉截铁的结论
- ❌ 在错误的层打转（中间层日志 ≠ 真证据），却以为已经"看过了"
- ❌ 甩锅外部（模型 / system / 服务）先于查自己路径特有的代码
- ❌ 同时改多个变量
- ❌ 找台阶（"日志没记""可能模型问题"）代替直接验证
- ❌ 被用户 / 同事质疑时绕，而不是顺着质疑往下挖——质疑往往指向你跳过的那一层

## 下结论前的自检（5 问）

1. 这是"我**验证过**的"还是"我**推断**的"？
2. 我手里的证据是**哪一层**？是最终实际输出，还是中间层？
3. 工作路径 vs 失败路径，差异我**逐层**确认了吗（含日志没记的字段）？
4. 失败路径有没有**自己特有的代码**（adapter / 包装 / 转换）我还没查？
5. 我这次打算改**几个**变量？（>1 个就先减到一个）

## 典型教训（真实案例）

> **现象**：CLI 路径的 LLM 工具调用失败（模型用文本"表演"工具调用），gateway 路径正常。
>
> **走过的弯路**：反复假设 system prompt / tools 数量 / thinking mode / tools 顺序 /
> "模型非官方"，每次都改了再测，全失败——因为一直在**应用层日志**（它记的是 agent
> 准备的 tools=39）上对比，而真正的 HTTP body 里 tools=0。
>
> **真根因**：CLI 特有的 `ProviderAdapter.chat` 把 tools 参数丢了（参数名 `_tools`
> 丢弃 + 传 `&[]`）。gateway 用的是另一个 adapter，所以正常。**只 CLI 失败 = CLI
> 特有代码问题**，第一时间就该查 CLI 的 adapter，而不是怀疑模型。用一行 eprintln
> 抓真正的 HTTP body，5 分钟就定位了。

## 遮蔽类 bug：没被发现 ≠ 没有（2026-11-21 幻影通告案例固化）

上面的纪律管「已知 bug 怎么找根因」；本节管另一类更阴险的问题：**bug 早就存在，但被多层机制遮蔽，很久之后才暴露**。典型真实案例（2026-11-21 根治）：后台任务完成通告被准入闸当用户消息——假 ⏳ 回执 → 幻影 user 行落盘 → 幻影 LLM 轮烧 usage——**存在 12 天、真实事故形态是 14 条通告连环排队**才被发现。

### 为什么没发现：遮蔽是逐层叠加的（每层单看都"合理"）

四层遮蔽链（复盘实录）：

1. **静默期**：功能引入 commit（d189e9e95，2026-11-09）只加了通告**发布**，没配准入**语义**——发布方/准入方的契约缺口从引入那一刻就存在。但此前的"世界"里通告根本不发，所以没人见过异常形态。**"只做了一半"的功能提交是遮蔽类 bug 的典型出生地。**
2. **显示层修复掩盖**（最关键的一层）：12 天后有人发现"系统注入渲染成用户气泡"并修了显示面——准入语义没动；修复时写下注释「通知轮是真实轮次（设计意图）」——**一条听起来合理的注释把缺陷冻结成了"设计"**。此后所有读代码的人（包括 AI）都会把幻影轮当成故意的，彻底失去怀疑动机。
3. **诊断工具滞后**：能暴露"通告在排队"的唯一 UI 面（⏳ 排队回执）在 bug 引入 12 天后才被造出来——在那之前排队完全不可见（无回执无徽标无痕迹）。**观测工具的存在时间窗决定了 bug 的可见时间窗。**
4. **触发密度**：只有重度后台构建负载（长任务期间连续完成通告）才连环触发；轻度使用偶发一条通告，混在正常消息流里毫无违和感。

### 它为什么躲过了测试：跨层缝没有主人

- 发布侧单测绿：消息确实发到了 bus ✓
- 闸门侧单测绿：`channel=="system"` 的豁免规则工作正常 ✓
- **但没有一条测试把"真实 wire 形态"的消息从 A 打进 B 的入口**。真实通告的 channel 是**来源通道**（web/rpc/...）而 sender 才是 system——恰好落进豁免规则的判定盲区。
- **两侧各自绿 ≠ 缝合处绿。缝上的 bug 不属于任何一侧单测的射程**，也没有任何人有义务看缝。
- 兜底面同样缺位：agent-bench 16 场景无此景；usage 无程序化告警（97→109 的 token 跳变无人察觉）。

### 如何能发现（固化成纪律）

1. **发布方/准入方契约纪律**：任何新的"系统侧消息生产者"落地前必须回答：**下游每个消费方对这条消息的字段形状做了什么假设？** 答不出来 = 契约缺口，先补齐（配语义 + 配测试）再合入。每条跨模块消息流必须有一方被指定为"契约主人"。
2. **跨层缝测试**：两个模块各自单测绿之后，**必须补一条把 A 的真实输出（真实 wire 形态，不是测试内手搓的理想形态）喂进 B 入口的测试**。这是防遮蔽性价比最高的手段——本案例一条测试就能提前 12 天抓住。写测试时问自己：我喂的是"生产方真的会发的形状"吗？
3. **显示层修复时横扫消费面**：修"显示不对"时先问：**这个形状还会流到哪里？** 列出全部下游消费方逐一检查。只修显示 = 把 bug 推进更深的地板下，还顺手给它盖了"修过了"的章。
4. **"注释合理化"警报**：读到把异常行为解释成"设计意图"的注释时，追问：这是谁拍板的？决策记录在哪？**找不到拍板记录的"设计意图"高概率是缺陷被合理化**，立单核实再继续。
5. **可观测性哨兵**：usage/token 跳变、消息数异常要有程序化告警或定期看账的纪律；"看起来合理但从没见过的 UI 产物"（bot 确认一条没人发的消息）本身就是 bug 报告，不要习惯化。
6. **考古方向**：复盘"为什么没发现"时，查**消息类型/字段的 git 历史**（不是文件历史），找生产方与消费方语义分叉的那个 commit——遮蔽类 bug 的引入点几乎总是一个"只做了一半"的功能提交。

### 修复后的横扫自检（防"修一半"）

修完闸/守卫类逻辑后，**沿消息流走查该闸的全部臂**（上游臂、同级臂、下游臂）：这个形状在每一臂会被怎么处置？事故路径通了不算修复正确——**同族路径全通才算**。实录：首修只修了 busy 闸（事故发生地），复查才发现 snooze 暂停闸在 busy 闸之前，同款病灶（假 💤 回执 + 幻影留痕）残留一条臂——"在你修的位置之前还有别的臂吗"是必修问句。

### 同类横扫的正确方法：先签名、再通篇盘点、后逐点分析（2026-11-21 二次纠正）

只扫"同闸邻臂"或"相关附近的点"是**局部横扫**，会漏掉散落在仓库各处、共享同一触发机制但没有显式关联的点。正确方法四步，**顺序不可颠倒**：

1. **先刻画触发签名**：当前问题是怎么触发的？提炼成可判定的形状条件（例：幻影通告 = 内部生产者 × 非系统通道形状 × 被用户消息语义消费）。签名不准，盘点必歪。
2. **通篇盘点同类触发点**：按签名（不是按文件邻近性、不是按 import 关系）全仓搜索——所有满足"签名条件 1+2"的生产点一个不漏。用 grep 找**构造点**（谁在造这个形状的消息/调用），不是找名字相似的字。
3. **逐点缺陷分析**：对每个盘点到的点回答：它的形状走到每个消费方会被怎么处置？哪些条件缺一？（满足签名全部条件 = 确诊同族；缺消费条件 = 理论面，记录碰撞窗口；形状不同 = 安全，写明为什么安全）。**"安全"结论必须附理由**，不是没看就是安全。
4. **最后统一处置**：确诊点给修复方案；理论面记录窗口大小与前置条件；设计取舍项（如回执政策）列选项交拍板。**先报告再动**——横扫报告本身是交付物。

反例实录：幻影通告首修横扫只走了"同闸上游臂"（snooze），漏掉了 goals 引擎注入（同款 unstamped 指令注入、busy 撞车吃同款 ⏳ 回执 + Reject 幻影双行）——它不在闸附近，只有按"生产点构造"grep 通篇才能找到。

---

**一句话总结**：证据要追到"真正用出去的那一层"，差异要逐层对比，一次只改一个变量，
自己的代码先于外部被怀疑；对遮蔽类 bug——缝上必须有测试，"设计意图"要有拍板记录，
修显示要横扫消费面，修闸要走查全部臂；同类横扫要先签名、通篇盘点、逐点分析、最后处置——
只扫附近的点 = 没扫。
