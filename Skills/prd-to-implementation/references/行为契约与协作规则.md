# 行为契约与协作规则

作者：NemesisZoo

## 目的与适用边界

把关键业务规则表达为开发者可实现、验收者可检查的契约，优先用于状态变化、业务不变量、重试与并发、关键查询以及跨模块协作。简单 CRUD 可合并为少量条目；仅解释静态结构时无需机械展开所有字段。

从业务目的开始，按“输入与条件 → 动作 → 状态及输出 → 不变量与观察点”表达。推荐模块、接口和机制均需与需求区分。每项行为保留唯一权威定义，其他文档按编号引用，避免接口说明、任务卡与验收分别改出不同规则。

本文件借鉴概念设计的行为表达和组合核验，不强制概念间禁止调用、独立存储、专用 DSL、固定目录或异步实现。完整 Concept design 可作为架构备选方法提出，须说明适用性、代价及与现有架构的关系，并按多方案决策机制选用。

## 行为契约的最小内容

给关键契约稳定编号，例如 B-001，沿用项目已有编号体系。至少回答下列适用问题；缺失业务规则标为待确认，不能靠示例或实现细节补成已确认需求。

| 方面 | 必须说明的业务语义 |
| --- | --- |
| 目的与依据 | 服务谁、完成什么可观察的业务结果；关联需求、来源及当前是事实／建议／假设。 |
| 状态与归属 | 谁拥有状态、身份如何区分、初始状态及合法状态；跨模块只引用身份时，不据此假定共享模型或数据库。 |
| 输入与允许条件 | 字段与对象、身份／权限、前置状态、约束和资源条件；条件不满足时如何回应。 |
| 成功效果 | 提交后哪些状态改变、输出何物、返回的标识与基数、外部副作用有哪些；关键不变量由谁保障。 |
| 保持不变的内容 | 哪些已有对象、字段或关系必须保持；允许的审计、失败计数等变化应明确列出，不笼统要求所有系统状态绝不变化。 |
| 拒绝与部分失败 | 拒绝是否无业务写入；已部分提交、超时或结果未知如何表示与核对；错误响应本身不能证明已回滚。 |
| 重复与并发 | 重复身份和去重范围、再次执行是无操作／拒绝／返回原结果／产生新效果；并发冲突如何判定及原子性边界。 |
| 核验 | 前后数据、返回值、可观察副作用、业务结果和证据位置；关联实现任务及验收用例。 |

只读查询补充：结果是零到多条还是至多／恰好一条、无匹配时的返回、排序和分页边界、是否受权限过滤，以及查询不改变业务状态的约束。示例不能替代完整规则；返回错误也不必然是实体的新状态。

## 跨模块协作规则

对每条重要协作说明以下内容，可用自然语言表格或时序图，不要求采用特定技术。

| 方面 | 需要明确的内容 |
| --- | --- |
| 触发点 | 发生请求、动作成功、事务提交、事件持久化、消息发布或其他哪一时点才触发？依据来自哪里？ |
| 条件与映射 | 哪些业务条件成立；身份、字段和查询结果如何映射；无匹配、多匹配或条件不满足如何处理？ |
| 后续动作 | 谁调用／编排，发起什么动作，产生什么状态或外部副作用；由谁拥有相关状态？ |
| 完成语义 | 已调用、已接收、已提交、已发起通知和已送达分别代表什么；对上游承诺到哪一步？ |
| 失败责任 | 超时、部分成功、重复、乱序、取消和补偿由谁处理；重试身份、次数／窗口、停止条件及后续核对方式来自何处？ |
| 组合不变量 | 跨模块是否仍满足各自契约和应用级业务结果；单模块成功不足以证明整体目的已实现。 |

机制可选择直接调用、应用编排、数据库事务、事件或队列等；行为规则不等于技术选型。没有已定的原子性或交付保证时，提出选项与验证，不能因画了箭头或使用某中间件就宣称保证成立。

## 从契约生成实施与验收

1. 依据源需求确定应观察的业务结果，契约补充或变更需显式记录。已有实现与预期不一致时保留差异，不能改契约掩盖缺陷。
2. 把每个关键条件、不变量和适用失败结果关联到负责模块、实现任务与具体操作；明确怎样保障原子性、识别重复或进行核对。
3. 按风险覆盖成功、边界、拒绝、重复、并发，以及适用的部分失败／重启／取消。只安排相关场景，不为无此行为的功能编造流程。
4. 用确定的输入、前置状态、预期状态和副作用设计用例。并发场景说明必须成立的结果集合，不假定无法从业务规则保证的请求完成顺序。
5. 核验业务目的、单项契约及组合结果，分别保留证据；状态未变不等于外部副作用未发生，语法正确不等于业务正确。
6. 方案阶段标为待执行；范围、实现或协作机制变化后，重新检查契约、任务、验收及证据的适用性。

按 [开发自测与测试策略](开发自测与测试策略.md) 将上述判据映射到适用 UT、真实边界 IT 和端到端 ST。Mock/Fake 可以验证依赖受控时的行为，真实事务、协议或平台约束需安排相应真实验证；复用契约场景核对替身，不将被测实现或替身的输出自行当作唯一正确答案。

## 简短示例：状态幂等与副作用不是同一件事

以下为教学假设，不是任何实际 PRD 的已确认要求：任务只能从未完成变为完成；重复完成不应再次发起通知；通知是否送达不阻塞任务完成。

| 动作／情形 | 预期结果与观察点 |
| --- | --- |
| 首次完成合法任务 | 任务变为完成，发起一次通知；其他任务不变。 |
| 再次完成同一任务 | 状态仍完成，且通知发起次数不增加；仅检查状态无法验证这一点。 |
| 完成不存在的任务 | 按已定错误契约拒绝，既有任务不变，不发起通知；实际错误格式须来自项目契约。 |
| 两次请求并发完成 | 应有一次有效状态迁移和一次业务通知发起；具体保障机制需设计验证，不能由假设直接宣称已实现。 |
| 发起通知后交付失败 | 不把“已发起”写成“已送达”；任务完成保留，通知恢复策略与去重身份另行明确。 |
| 返回超时且提交结果未知 | 通过相同操作身份或结果查询核对，不能简单认定未提交后再发一次副作用。 |

示例中的“任务完成”和“通知发起一次”属于业务规则，重试传输、重复投递与外部通道去重如何协作仍需机制和证据。若真实 PRD 要求每次完成调用都通知，应按真实规则编制，不能套用教学假设。
