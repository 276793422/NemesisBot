# 工作流程

作者：NemesisZoo


按依赖顺序完成以下工作。小项目可以合并章节，但不得遗漏适用步骤的实施细节、衡量标准和输出物。关键选型未定时，按多方案决策规则先交付评审包，后续步骤区分公共部分和条件分支；选定后补齐完整实施方案。编写交付文档时读取 [软件实施方案模板](软件实施方案模板.md)，按项目裁剪并填写实质内容。

涉及关键多选路线时读取 [多方案决策](多方案决策.md)。以下“可实施”“任务完整”等衡量标准用于本次声明可执行的范围；评审包中的待选分支明确差异和待补项，不冒充已经满足完整实施条件。

### 第一步：建立需求与约束基线

**实施细节**

- 提炼目标、范围、角色、场景和核心业务规则；保留 PRD 原有编号，为缺失编号的需求分配稳定标识。
- 将复合需求拆为可分别判定的子项，保留与原文的关系；新增推导需求注明推导理由和确认状态，不将其冒充 PRD 原文。建立“原始需求 → 本期／后续／排除／待确认”的处置映射，排除或延期须有范围依据，不能静默删去需求来提高覆盖率。
- 区分功能需求、非功能需求、外部约束和排除项；识别冲突、遗漏、不可测试的描述。
- 建立需求清单、质量目标表和问题／假设清单，标明来源、优先级、状态与验证方式。
- 建立生成约定和来源清单，区分当前交付、仅预留边界及未来演进；声明资料读取限制和默认值。
- 识别实际涉及的项目类型及部署约束，读取 [项目类型专项检查](项目类型专项检查.md) 的公共规则和相应小节；记录适用性、已有依据及缺失输入，不将所有专项项默认为项目需求。
- 读取 [开发自测与测试策略](开发自测与测试策略.md)，识别已有测试框架／术语与实际基线、CI 和环境／数据／外部依赖条件；新项目记录待建立项，为 UT/IT/ST 和真实联调预留准备任务。
- 为后续追踪设置稳定编号，例如需求 R、质量要求 Q、模块 M、决策 ADR、任务 T、验收用例 AC；已有项目编码体系优先沿用。

**衡量标准**：可读取范围内的原始需求均有明确处置，未解析范围已披露；本期需求全部有来源、编号、优先级和可判定的验收条件，或明确标为待确认；所有关键冲突均登记影响、处理建议及确认节点，不存在未披露的关键假设。

**输出物**：生成约定、来源清单、需求基线、范围与排除项、质量目标表、问题与假设清单、测试基线与资源约束。

### 第二步：梳理业务域与关键流程

**实施细节**

- 识别业务能力、职责边界、统一术语、关键实体和数据归属。
- 复杂业务确定限界上下文、聚合与事务边界、业务不变量、领域事件及上下游关系；简单业务说明为何采用更轻量的建模方式。
- 描述核心用例的正常路径与适用的失败路径，包括权限拒绝、重复请求、超时、并发冲突和外部依赖失败。
- 明确跨模块协作契约、一致性要求和状态变化；异步协作说明幂等、重试、补偿、顺序或重复事件处理。
- 对关键写操作、状态迁移和跨模块协作按 [行为契约与协作规则](行为契约与协作规则.md) 定义条件、效果、不变量、保持不变的内容、拒绝、重复及部分失败；查询写明结果基数、空结果和顺序，协作写清触发点与完成语义。
- 从关键契约导出测试输入、前置状态、预期结果及观察点，初步区分单元可证明的规则、需要真实集成验证的约束与系统级业务结果；不只从实现代码反推预期。

**衡量标准**：每个核心用例均能定位职责模块、输入输出、关键规则和异常处理；关键数据有明确归属，核心业务不变量具有实现位置和验证办法。

**输出物**：业务域／模块职责表、关键流程图或时序图、业务规则与数据归属说明、关键行为契约及协作规则。

### 第三步：选择架构并记录关键决策

**实施细节**

- 根据业务复杂度、团队能力、规模、一致性及运维成本选择架构；分层、六边形、洋葱、模块化单体、微服务、事件驱动和 CQRS 均为可选工具，不是必备组件。
- 按主文件的设计层次分别评估整体组织、依赖结构、业务建模及表现层模式。有交互界面时按 [专项检查](项目类型专项检查.md) 比较适用的 MVC、MVP、MVVM、MVI／单向数据流或轻量状态组织，说明与领域／应用层的组合关系，不把 MVC 与微服务或 DDD 当作同一层面的二选一。
- 先按硬约束筛选可行性，再比较方案的需求适配、实现与运维成本、风险、可逆性和演进成本。硬约束不满足不能用其他优点或加权总分抵消。
- 充分展开有实质差异的可行选项，按多方案决策规则组织评审与决策，不将选项数量限制为两个；仅有一个可行选项时说明其他选项的排除理由，无须凑数。没有可行方案时明确结论，给出需调整的约束或验证项及影响，不擅自放宽需求后声称可行。
- 整体可行性未成立时，交付冲突诊断、验证／约束调整建议及可独立推进范围；受影响的详细设计和排期保持条件化，不假定前置问题已经解决。
- 若用户或现有系统已固定总体架构，在该约束内比较有实质差异的实现路径，避免重复争论已确定事项。
- 用适当层级的 C4 图说明系统上下文、可部署单元、数据存储和外部依赖；复杂模块补充组件图。优先使用可维护的 Mermaid，并以文字解释边界与关键箭头。
- 对高影响或高迁移成本决策编写 ADR，记录背景、约束、候选项、决定、理由、后果、状态与复审条件。
- 将关键决策关联到来源、需求、假设及核验办法；明确哪些结论已被材料支持，哪些仍依赖原型或后续实测。
- 对重要架构约束列明允许／禁止的依赖或状态访问、检查范围与办法、负责检查的任务及违反后的处理。可采用契约审阅、依赖／构建检查或相关测试；有仓库时沿用可用工具，没有时说明待建立的办法，不伪称现有命令。仅有架构图或模式名称不足以证明边界成立。
- 在选型时设计可独立构造的单元、外部依赖接缝、状态／故障观察点及真实边界验证；比较测试隔离成本、环境可获得性、替身维护与框架支持。高风险可测试性假设安排前置验证，不等功能完成后再决定是否能 Mock/Fake 或联调。
- 写明演进触发条件，例如容量、独立发布需求或团队边界变化；不用无依据的增长预期驱动提前拆分。

**衡量标准**：候选全景及筛选理由可追溯，每条实质不同的可行路线均有可比较的方案卡；推荐及备选均说明需求适配、代价、风险和适用条件；图、模块、技术组合及 ADR 在各自分支内一致；待选决策有明确选项及决策材料，所选方案有实际选择或授权依据；领域分层依赖方向可检查，偏离有理由与影响说明。

**输出物**：候选全景与筛选理由、多方案对比与方案卡、架构图及技术组合、模块边界与依赖规则、测试边界／接缝与依赖替换策略、关键 ADR、待决清单／选型记录、演进策略。

### 第四步：细化到可实施的技术设计

**实施细节**

- 按模块明确职责、对外契约、内部关键组件、数据读写责任及对应需求。
- 交互模式适用时，定义视图、Controller／Presenter／ViewModel 等职责，区分业务／共享／页面状态及其权威来源、生命周期，明确事件和异步结果流、晚到结果处理、加载／错误／取消及页面重建行为；给出任务与验收观察点，不将取消等待等同于业务回滚，不把业务规则复制到各界面实现。简单项目可合并职责实现，不强制逐项创建独立层或类型。
- 定义关键接口或事件的调用方、输入输出、鉴权、错误语义、版本及兼容策略；状态写入定义事务边界、并发控制和幂等策略。
- 设计核心数据结构、关联、索引依据、生命周期及必要的数据迁移方案；只展开支撑本期需求的细节。
- 根据实际需求补齐安全与权限、配置与密钥、日志指标与链路、备份恢复、部署及故障处理设计。
- 将命中的专项检查及行为契约落实到机制与验证计划；必要时比较自研、已有库或服务的实际代价，技术成熟度、团队维护能力和运行责任纳入取舍，不以默认组件代替分析。
- 对不确定且影响大的技术点安排验证性原型，给出待验证假设、时间盒、实验条件、通过阈值和失败后的替代路径。
- 形成 UT/IT/ST 测试矩阵、真实依赖与 Mock/Stub/Fake 清单、契约一致性核对、数据／环境初始化与清理、时钟／调度等可控点及本地／CI 入口。接口测试按真实验证范围归层，写明目标引擎／协议／硬件版本和不能被替身证明的内容。

**衡量标准**：开发者能够据此实现核心链路，无须猜测业务规则、数据归属和接口语义；关键质量要求及高风险依赖有适用测试层级、环境、判据和验证任务；重要替身有真实契约核对办法，高风险可测试性假设仍待验证时不假称已可测；不适用项说明原因，不为填满模板引入额外系统。

**输出物**：模块详细设计、关键接口／事件契约、核心数据模型、质量属性与运行设计、分层测试与自测策略、数据／环境和执行入口设计、技术验证计划。

### 第五步：编排开发计划

**实施细节**

- 将范围分解为里程碑、工作包和可独立检查的开发任务。优先形成可运行的端到端业务切片，再扩展能力。
- 任务粒度以指定执行主体能够独立执行、提交和检查为准；若仍需自行决定关键业务规则或架构取舍，应先补充设计或拆出前置决策任务。无需强行规定统一时长。
- 排序同时考虑业务价值、技术风险和依赖关系；将可能引发架构返工的原型与关键外部集成验证安排在依赖它们的大规模开发之前。
- 每项任务标注需求、模块、前置依赖、负责角色、工作量区间、交付物、完成标准和验证方式；按需覆盖设计、实现、测试、集成、迁移、发布与交接。
- 明确依赖和可并行范围，识别关键路径、外部阻塞、测试环境与集成资源需求。
- 估算写明人员技能、可用投入、复用基础、评审与返工等假设。区分工作量与自然工期，不把人日直接当作日历天数。
- 团队或起始日期不明时提供相对顺序和条件化工期，不虚构负责人姓名或承诺日期。
- 明确第一个端到端切片覆盖的核心场景、异常路径、接口和数据流，以及演示方法、通过标准和证据。
- 对适用专项要求安排实际验证任务、环境及产物；关键行为契约关联到实现和验收任务，不能只留在设计附录中。
- 将 UT、相关 IT、系统切片验证、替身及真实契约核对、夹具与环境／CI 准备纳入任务和工作量；按变更与风险确定适用范围，测试与功能同步推进，不能统一压到末尾。提前明确真实联调资源、进入／退出条件及执行角色。

**衡量标准**：本期需求全部分配到任务及验收用例，支撑性任务明确服务于哪项质量目标或风险；任务均有完成定义，依赖无环且无未解释的遗漏前置项；里程碑有进入条件、退出条件和可演示成果，排期符合已知资源约束。

**输出物**：里程碑表、任务分解与依赖关系、工作量／排期估算、资源与风险安排。

### 第六步：编写逐步实施说明

**实施细节**

- 将开发任务展开为有序操作，按模板的“任务卡”和“实施步骤表”填写。
- 每项开发任务包含“核对契约和测试基线 → 准备接缝／数据／环境 → 实现及适用测试 → 本地自测 → 失败修复与回归 → 提交结果”的自测闭环，引用具体 UT/IT/ST、命令／步骤及证据位置；任务完成定义不能只写编码结束。
- 根据执行主体补充交接信息：人工任务说明职责与评审点；AI 任务提供最小上下文、关联契约、建议修改范围、禁止越过的边界、适用验证命令及停止条件；混合任务明确何处由人判断及交接哪些产物。例行实现选择允许执行者依约判断，关键需求冲突或权限缺失须保留为阻断项。本条不自动授权启动其他代理或外部操作。
- 每一步必须有：前置条件与输入、具体操作、衡量标准、验证方法、输出内容及保存位置；指定执行或检查角色，注明适用的失败处理／回退办法。
- 操作具体到可分工执行，例如定义何种契约、实现何种校验与状态迁移、怎样验证拒绝或失败场景；不能只写“完成后端”“做好测试”。
- 已知仓库时引用真实目录和现有命令；新项目可提出建议目录及命令，但标明建议或待验证。未检查的路径和工具不得声称已存在。
- 根据项目补齐环境准备、主干链路、分批集成、系统验证、数据迁移、发布与交接步骤。迁移或发布步骤说明验证点、停止条件及回退条件。

**衡量标准**：所有任务都有可执行步骤，每一步均有输入、操作、可判定标准和输出物；开发任务的适用自测、回归、结果记录与完成条件明确；必需测试失败、跳过或缺环境时保持受阻／未完成范围，不能记为全部通过；需验证结论均指定证据，失败后能判断返工、回退或等待哪个前置条件。

**输出物**：逐任务实施卡、逐步操作与验证表、适用的迁移／发布／回退说明。

### 第七步：设计最终验收并完成一致性检查

**实施细节**

- 建立需求追踪矩阵，关联需求、模块、任务、验收用例与证据位置；检查孤立需求、无依据任务及不可验证指标。
- 将适用 UT/IT/ST 与最终验收分别关联，核对测试所用版本、环境、数据、真实／替身范围及报告；Mock/Fake 全绿不能代替关键真实集成，ST 通过不能直接替代最终业务验收。项目测试证据与本技能自测记录分开管理。
- 分别定义“方案验收”和“软件验收”。方案验收检查生成约定、来源与推导可追溯、需求覆盖、任务可执行性、验收可操作性及文档一致性；软件验收依据实现版本、实际测试、运行证据和交付物形成结论。
- 多方案阶段分别检查评审包的决策准备程度、公共任务的执行条件及各分支限制，不把待选方案判为已具备全部实施条件。业务验收目标跨方案保持一致，技术验收办法可随方案变化；选定后检查正式计划与所选组合一致。
- 定义验收范围、版本、环境、测试数据、执行角色、前置条件、步骤、预期结果、阈值、证据和判定规则。
- 按需求覆盖功能与业务不变量、端到端集成、适用的性能与容量、安全权限、恢复与部署、可运维性及交付完整性。
- 性能指标写明负载模型、数据规模、持续时间、统计口径（如 P95）、环境和阈值；覆盖率等指标说明分母，不以代码覆盖率替代业务正确性。
- 验收用例分别给出预期结果的依据、执行操作和观察点；覆盖会暴露设计缺陷的关键反例。不得仅因实现不达标就降低基线阈值；合理变更应记录来源、影响及明确接受依据，并重新核验。
- 按行为契约检查成功、拒绝、重复、并发及适用的部分失败结果，包括应保持不变的业务数据和外部副作用；按命中专项检查核验目标环境、数据及资源条件。将“调用完成”“状态已提交”“消息已发起”“已送达”分别判断，不能互相代替。
- 明确缺陷分级、阻断条件、例外接受权限、整改与复测流程；默认关键业务用例全部通过、无未解决的阻断／严重缺陷，例外须有明确接受依据。
- 定义验收结论如何形成、由谁确认及验收记录模板。方案阶段未执行项目标为“待执行”，只能得出方案是否具备实施／验收准备条件。

**衡量标准**：目标为本期基线中功能与质量需求的有效追踪覆盖率 100%，同时检查原始需求处置与材料解析范围；达不到时列出缺口和阻断范围，继续交付标明限制的方案，不伪造达标结果。关联内容须实质支持相应需求；关键结论有可定位依据或显式假设及核验办法；未确定阈值和待确认事项单列，不计为已满足；验收标准有独立的预期依据、可执行方法和证据要求；文档各部分保持一致。各项覆盖率明确分母；分母为空时写明无法计算，不能填为 100%。
