# 开发自测与测试策略

作者：NemesisZoo

## 目标与适用边界

在架构阶段定义所设计软件如何被测试，将 UT、IT、ST、测试接缝、数据、环境和自测证据落实到开发计划。此文负责软件开发测试设计，不是本技能的行为评测记录；用户只要求方案时，不据此擅自编写功能、运行项目测试或操作外部环境。

沿用项目已有术语、测试框架及可用工具，必要时明确与下列口径的映射。小项目合并场景和工具，复杂项目按风险分层，不能只列测试名称而缺少对象、预期和执行条件，也不要求每项功能重复实现所有层级。

## 一、区分测试范围与依赖替换方式

| 范围 | 主要证明什么 | 典型对象与条件 | 不能据此直接证明什么 |
| --- | --- | --- | --- |
| 开发自测 | 本任务在约定范围内满足契约，提交内容和验证结果可交接 | 开发者在任务内执行适用的构建／静态检查、UT、相关 IT 与必要链路验证，并整理结果 | 它不是与 UT/IT/ST 并列的固定第四层；个人判断不代替必需的实际测试证据。 |
| UT：单元测试 | 可独立验证单元的规则、状态迁移和错误语义 | 领域规则、应用分支、转换或交互状态；按需要隔离外部 I/O，采用确定性输入与可观察结果 | 替身模拟的数据库约束、协议兼容、跨进程事务、生产容量或真实副作用。 |
| IT：集成测试 | 指定的真实组件或边界组合能按契约协同工作 | 应用与目标数据库、真实存储适配、序列化与传输、消息适配或上下游契约；使用隔离的相容实例／沙箱 | 未接入的真实依赖、完整部署链路以及未测试的版本与负载。其他依赖可替换，但必须说明真实集成覆盖到了哪里。 |
| ST：系统测试 | 可部署／可运行系统从约定入口满足端到端需求及适用质量目标 | CLI、API、GUI 或设备入口，覆盖关键业务、安装／升级／恢复和实际适用 NFR；使用代表性系统环境 | 被替换的外部通道或硬件的真实兼容／容量，以及未执行的业务最终验收。 |

接口/API、契约、性能、故障注入等是测试对象或方法，并不天然等于 IT 或 ST；按实际被测范围标记。采用替身的组合测试可以有效验证内部集成，但需明确其覆盖范围，不能宣称真实外部接口已联调通过。

## 二、架构阶段设计测试边界与接缝

从关键业务契约和风险出发，为需要独立验证的边界建立以下设计：

- **构造与依赖装配**：可单独构造业务用例或状态单元，并在合理位置提供依赖替换。可使用参数、函数、配置、已有端口／接口或框架支持，不要求每个类新增接口。
- **外部 I/O**：数据库、HTTP、消息、文件、设备和平台 API 的责任明确，业务单元不会因为导入模块就启动服务器、连外部系统或访问真实设备；适用时将初始化移到明确装配点。
- **时间与不确定性**：时钟、随机值、生成身份、调度和超时按测试需要可控；并发测试设计可复现的协调与断言，避免靠任意长等待碰运气。
- **数据与观察点**：能准备前置状态、触发失败并查询业务结果；必要时有合法的测试夹具、查询端口或隔离诊断方式，不为测试扩大生产公开接口或绕过权限。
- **事务与故障**：能够在关键提交边界观察或注入失败，明确失败前后允许的状态；仅在内存 Fake 中表现为“原子”不能证明真实事务行为。
- **界面与平台**：界面状态转换尽量可独立验证，导航、异步、取消和生命周期另以组件／系统场景覆盖；硬件或平台不可模拟的部分预留目标环境测试。

对每个重要接缝说明它支持哪些 UT/IT/ST、由谁实现和维护、产物位置以及怎样检查其可用。高风险接缝或工具能力不明时安排前置技术验证任务并给出通过条件；方案阶段不能把待验证的设想标为已经可测。

测试可行性、隔离成本、目标环境可获得性及维护成本应进入架构备选方案对比。选定后把对应准备工作纳入依赖与估算；测试基础设施不能全部推迟到功能集成之后。

## 三、真实依赖与测试替身

| 选择 | 适用目的 | 要明确的限制与维护办法 |
| --- | --- | --- |
| Mock | 控制依赖响应，验证重要的调用协议或业务副作用次数 | 只断言与业务契约有关的交互，避免绑定私有调用顺序；模拟返回不证明真实依赖接受该调用。 |
| Stub | 提供确定输入或固定的成功／错误响应 | 说明响应来自哪个契约／版本，覆盖相关错误、空值和边界，不只返回成功。 |
| Fake | 用简化但可工作的替代实现支持状态性测试，如内存仓储 | 明确与真实实现的差异，尤其事务、排序、唯一性、并发和持久化；通过相同契约场景或针对性真实 IT 核对差异。 |
| 真实隔离实例／沙箱／硬件 | 验证实际适配、协议、存储或平台约束 | 标明版本、配置、数据和访问条件，与交付目标不一致的差异须披露；范围与授权按项目约定执行。 |

为重要替身记录依赖名称、契约来源／版本、真实与替代实现、选择理由、差异、核对办法及负责角色。Mock/Fake 不代替另一方提供者契约或真实集成验证；内存 SQLite 也不能自动代表 PostgreSQL 等不同目标引擎。

优先复用行为契约测试场景、真实错误样本和兼容的公共夹具校验替身，按变化影响更新。协议、适配、数据模式或替身自身变化时复核相关 UT 与真实 IT，避免替身与生产实现一起漂移而测试仍然全绿。不能把真实依赖难以获取作为宣称已集成通过的理由。

## 四、测试数据、环境与执行入口

在详细设计中明确，并按实际需要设置准备任务：

- 代表性正常／边界／非法／重复／并发数据、参考结果与数据版本；预期来自需求或已确认契约，不由被测实现自动生成唯一判据。
- 每层所需运行时、库、数据库／服务／设备版本与配置，真实和替代依赖分布，以及与交付环境的差异。
- 可重复的初始化、隔离身份／数据目录、清理、重置与失败后的资源回收，保证用例可独立运行，避免顺序依赖及污染共享数据。
- 环境配置、测试凭据与夹具如何获取和使用；测试数据采用适合该环境的来源与权限，不默认使用生产数据或共用可变实例。
- 本地和 CI 的运行入口、参数、选择范围、预期返回码、报告位置及诊断办法；已有仓库引用已核实命令，新项目标明建议入口和待建立任务，不伪称现有脚本。

离线、设备或外部服务资源缺失时，说明可先执行的测试、替代验证的限制、需要补测的项目和责任，保留待执行／阻断状态。

## 五、每个开发任务的自测闭环

在任务卡中给出以下适用步骤，而不只在最后安排一个笼统“测试阶段”：

1. **开发前核对**：核对需求、行为契约与验收预期，识别影响的单元和边界；已有项目检查相关测试基线，新项目登记暂无基线及待建入口。已有失败与本次新增失败分别记录，不把二者混为全绿。
2. **准备可测条件**：安排测试数据、装配接缝、替身、真实依赖实例及清理办法，明确哪些条件阻断当前任务；适用时先创建关键用例或技术验证，不强制所有项目采用同一种 TDD 顺序。
3. **实现与测试同步**：按同一业务契约实现功能及适用 UT、IT/契约测试和关键链路验证。把测试代码、夹具和环境工作纳入任务工作量，优先跑通包含失败路径的端到端切片。
4. **本地执行与语义自查**：运行项目已有且相关的构建／静态检查、受影响 UT、相关 IT，以及本任务必需的系统冒烟；按风险从快到慢增量执行，核对结果和副作用，不凭“编译通过”结束自测。
5. **失败处理与回归**：定位代码、契约、环境、数据或替身问题，修复缺陷时补充能暴露该缺陷的回归场景，再执行失败项及受影响层级。重复运行偶尔通过不证明稳定；不删除断言、放宽标准或忽略用例来制造通过。
6. **提交与交接**：记录实现版本、环境、真实／替代依赖范围、实际命令／步骤、测试范围、结果、报告及残留问题；让接收者能复核哪些已验证、哪些待补。方案阶段仅定义这份记录，不填虚构的实际结果。

任务完成定义包含其必需自测和相关评审。必需验证失败、跳过、缺环境或未执行时，该部分保持未完成或明确受阻，不能直接标记全部完成；确有范围豁免时需记录依据、接受责任和补测安排。与本任务无关的已知失败也应披露，不自动要求扩大实现范围。

## 六、CI、集成与系统测试的时机

按仓库工具、风险及资源规定触发策略和执行责任，例如提交／PR 运行受影响 UT 与适用快速 IT，集成里程碑运行相关真实 IT 和关键链路 ST，再在适用窗口执行完整回归、容量、恢复或目标硬件场景。这些是安排示例，不能将固定频率或工具当作所有项目要求。

UT 不必等待全模块完成，IT 从首个边界组合开始，ST 从第一个可运行业务切片开始并持续扩展；真实环境准备和外部联调窗口应提前排期。手工、GUI、设备在环或外部沙箱场景同样要给明确步骤、预期和证据。

对必需用例定义进入／退出条件和阻断规则，测试失败进入缺陷与复测流程。资源不可用、被隔离的波动用例、未执行或被跳过的场景单列，不计作已通过；不能以无限重试隐藏不稳定结果。CI 通过只证明该流水线实际执行的范围，性能和故障恢复结论需各自证据。

## 七、测试计划、衡量标准与交付

按 [软件实施方案模板](软件实施方案模板.md) 的测试矩阵组织，至少记录：关联需求／行为契约、测试对象及层级、关键场景与预期、接缝和真实／替身依赖、数据与环境、触发时机、执行角色、通过标准、入口和报告、准备／实现任务及未验证范围。简单项目可合并表格，不丢失信息。

不同阶段分别判定：

- **架构／计划准备**：关键规则及高风险边界均有适用验证层级，测试接缝、观察点、数据、环境与责任已设计；准备成本与依赖进入计划，高风险可测试性假设有验证任务。测试尚未执行不影响记录计划完成，但不能据此判软件已通过。
- **开发任务完成**：本任务要求的实际检查与测试通过、相关缺陷处理、结果可复核；缺环境和未执行按上述受阻规则处理。
- **集成／系统阶段完成**：约定必过场景与质量目标有对应版本、条件和报告，替身覆盖的局限与未测项已披露；关键真实集成不能由全部 Mock 的绿灯代替。
- **最终验收准备**：从 UT/IT/ST 结果到需求和最终验收建立追踪，确认仍有效的证据和待执行的业务确认。ST 证据可复用，业务验收结论与责任仍独立定义。

覆盖率、通过率及性能目标均说明口径、分母和来源；不默认 80% 或 100% 代码覆盖率，也不以测试数量替代业务覆盖。至少把本期关键不变量、重要拒绝路径及高风险集成列出对应检查，适用的重复／并发／失败结果有预期与观察点；不足之处明确列缺口。

测试交付按需包含：策略与矩阵、UT/IT/ST 用例及代码、替身与契约核对、夹具与数据说明、环境／执行入口、CI 配置、实际报告与缺陷／复测记录。方案编制时说明拟交付位置及任务；实施后才核对实际文件和结果。

## 示例：完成任务并保存一条通知意图

以下是教学假设：单应用及已定关系数据库中，“完成任务”和“创建一次通知意图”须原子提交；重复完成不新增意图。通知实际发送另有范围约定，不能由保存意图推断已送达。

| 层级 | 测试设计 | 预期及证据边界 |
| --- | --- | --- |
| UT | 用可控的状态／仓储替身验证合法完成、拒绝、重复操作和应用分支 | 核对任务结果、意图创建语义及其他数据不变；不能证明真实数据库原子性。 |
| IT | 接入目标版本数据库和真实适配器，在两项写入之间注入可确认失败，并验证重复／并发 | 观察真实回滚与唯一约束，确认没有半提交或重复意图；不能用 Fake 的表现代替。 |
| ST | 运行应用，从实际入口执行首次／重复完成、结果未知后核对及适用重启场景 | 核对端到端状态、意图计数和响应，记录部署与数据条件；未接入发送通道时不宣称通知送达。 |

这三层可共享业务夹具与预期，但各自验证不同风险。是否需要独立端口、事务单元或测试注入点，应在架构与详细设计阶段确定并落实到任务，不能留到最终接口测试时再猜测改造范围。
