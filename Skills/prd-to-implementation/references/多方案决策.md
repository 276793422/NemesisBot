# 多方案决策

作者：NemesisZoo

存在关键多选路线时读取；按模板中的候选全景、方案卡和选型记录组织交付。


- **触发范围**：对会实质影响业务能力、开发方式、部署运行、成本、工期或演进成本的多种可行路线启用。总体架构和关键局部选型分别记录，不将每个例行实现细节变成待人类审批项。
- **充分探索**：在需求与约束内，尽可能覆盖有实质差异的架构路线和相关技术选项，不固定只列两个或三个。先列候选全景，再说明可行性、差异和建议；被约束排除的选项及理由保留在简表中。未核实的候选标明待验证，不能当作已证实可行。
- **收敛条件**：对会影响本次决策的架构组织、部署、数据、集成及适用的交互状态模式等维度完成探索，已识别的实质不同路线均被登记、归组或有依据地排除，且新增候选只重复已有取舍时，结束本轮扩展并进入比较。关键差异无法判断时提出验证任务；剩余调研范围与限制明示。用户希望继续扩展或补充约束时再开展下一轮，不设固定选项数量上限。
- **控制组合复杂度**：用整体方案编号关联相容的组件选项，说明哪些可独立替换、哪些相互依赖或互斥。采用公共设计加差异说明组织内容；不机械枚举所有技术组合。合并近似选项时保留其区别及合并依据，附录保留候选全景，不静默遗漏未推荐选项。
- **统一比较口径**：各方案基于同一需求基线、硬约束和质量目标。每条实质不同的可行路线说明架构与关键技术组合、适用条件、收益与代价、依据及待验证假设、团队匹配、实施与运维成本、风险、可测试性与 UT/IT/ST 环境／替身维护成本、演进／替换成本，以及开发计划和验收方法的差异。无法估算项如实保留，不以缩减需求使某方案显得更优。
- **条件化建议**：说明“优先交付速度时倾向哪项”“优先独立扩展时倾向哪项”等与本项目实际有关的选择理由。给出专业判断，同时说明什么条件会改变推荐，不能只罗列技术名称或用无依据的排名代替分析。声明已考虑的维度和未调查范围，不声称穷尽所有可能。
- **选定前交付**：先完成多方案评审包，包含候选全景、对比与方案卡、公共设计、各分支计划及估算差异、关键验证任务和待决清单。公共实施任务及前置验证仍须写明步骤、衡量标准和输出物；依赖选型的任务保持分支与条件，不混成一份可直接执行的承诺。明确该包尚不等于选定后的完整实施方案。用户要求各候选完整详案时按要求展开，不自行缩减为评审包。
- **人类选择**：将待选问题整理成可直接决定的选项，指出选项编号、适用条件、关键代价、依赖项及决策影响，交由用户或其指定开发人员决定。先交付可审阅材料，再请求选择。已有明确选择或用户授权代选时按授权推进，并记录依据；否则不将推荐方案标为已接受，也不据此执行分支特有的开发或部署。
- **选择反馈**：允许选择现有方案、组合相容选项、补充验证或暂缓决定。用户选择混合路线时记录组合并重新检查硬约束、兼容性和计划影响；选择含糊且影响关键边界时仅澄清该处，不能自行解释为采纳推荐。选定架构只授权在当前任务范围内继续编制方案，不自动授权开发或发布。
- **选定后收敛**：记录选择者或授权依据、选项编号及版本、理由、接受的代价和未决条件；检查组合兼容性及硬约束。选择后沿用公共设计，细化所选分支的完整架构、开发计划、逐步实施和最终验收，更新 ADR、任务依赖、估算及追踪矩阵。其他分支保留为历史备选，不纳入当前执行计划；改选时按变更流程重算影响。
