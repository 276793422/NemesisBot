# sc-bugfix — BUG 修复六阶段纪律

修复看板指派的 BUG（单子 description 头部带【修复流程契约】）。本 skill 是六个
阶段的工程纪律清单：每阶段产出对应的证据标记，最终交付评论按标记汇总。任一
标记缺失 = 验收不放行，这是契约不是建议。

## 总纪律（贯穿全程）

- **证据分级**：推断 ≠ 结论。斩钉截铁下结论前必须有直接、完整的证据；模型表达
  的自信或概率本身不是证据。
- **事实/推测/待确认三分**：复述问题时区分「单子里写了的」「我推断的」「还没确认
  的」，不混写。信息不足时说明缺口，**不补造**操作、设备、版本或复现结果。
- **不把猜测包装成根因修复**：没有确认根因就改代码 = 症状补丁，宁可先取证。
- **过程留痕**：发现影响结论的关键事实、调整执行方向或遇到阻塞时，在回复里简短
  说明真实进展；只陈述公开行动、已确认事实和下一步。

## 阶段 ① 理解 `[UNDERSTOOD]`

复述 BUG 现象、复现路径与影响范围，落到证据上：

1. 确认问题来源与完整性：描述、附件、日志引用各自说了什么、缺什么（读取失败与
   原文缺失分开说明）。
2. 区分涉及的端/平台/版本：谁发起、谁接收、异常在哪个端。版本信息逐项核对，
   不合并不同环境的描述。
3. 明确复现路径：单子里给了复现步骤照着复述；没给的标注「单子未提供复现步骤」
   并给出从现象反推的最可能路径（标明是推断）。
4. 不在信息不足时编造：影响范围说不清就写「影响范围待确认（原因）」。

**本阶段结束输出 `[UNDERSTOOD]` + 三段：现象 / 复现路径 / 影响范围。**

## 阶段 ② 分析 `[ROOTCAUSE]`

定位根因到具体文件与代码路径，给出证据：

1. 建立对应关系表：现象 ↔ 触发条件 ↔ 代码路径 ↔ 观察结果，明确注明「能解释的
   部分」和「仍解释不了的部分」——解释不了的不是留白，是下一轮取证的入口。
2. 追完整数据流：确认日志/证据来自哪一层，不在不完整的中间层日志上打转。
3. 只一个路径失败 = 该路径特有代码问题；先查自己代码再怀疑外部依赖。
4. 证据不足但存在可验证线索 → 提出取证计划（要什么日志/跑什么复现），而不是
   硬猜根因接着改代码。
5. 根因结论必须落到：文件路径 + 代码位置 + 为什么这段代码在所述条件下产生所述
   现象。三者缺一 = 还没到 [ROOTCAUSE]。

**本阶段结束输出 `[ROOTCAUSE]` + 根因链（文件:位置 → 机理 → 现象）。**

## 阶段 ③ 开发

最小改动修复根因：

1. 先读仓库内的规范文件（AGENTS.md / CLAUDE.md / 目录级说明），按既有代码的
   命名、注释密度、惯用法写——像周围代码一样。
2. **只修根因路径**：不夹带无关重构、不顺手改格式、不动与根因无关的文件。
3. 改完横向扫同类：同一根因形态是否还有兄弟代码（复制粘贴出来的缺陷常成串），
   一并修或明确列出未修理由。
4. 维持单一真相源：不在两处维护同一逻辑；清理对称彻底（删逻辑就删干净引用）。

## 阶段 ④ 测试

运行或补充能证明修复生效的测试：

1. **目标缺陷直接断言优先**：基础功能/回归用例全绿 ≠ 目标缺陷验证通过。必须有
   能区分修复前后行为的断言（已有用例补断言，或新增针对根因的用例）。
2. 新增测试与既有测试同形态（同框架、同命名、同目录）；不引入新依赖解决小事。
3. 断言行为不押实现细节：换实现不换行为的断言才是可保留资产。
4. 缺口诚实记录：没有条件跑的测试（环境缺、依赖缺）列明缺口，**不宣称已通过**。

## 阶段 ⑤ 验证

全量门禁与既有回归，命令与输出原文贴出：

1. 跑仓库声明的门禁（构建 + lint + 相关测试），命令原文 + 输出原文贴出——不
   摘录、不转述「测试通过」。
2. 独立复查自己的 diff：逐文件过一遍改动影响面（调用方、协议对端、并发面、
   平台差异），主动检查受影响调用方。
3. 未执行项如实标注：跳过的检查写明跳过原因；没跑的写没跑，**不写成通过**。
4. 回归对照：改动是否破坏既有行为——相关既有测试全量跑，不只跑新增的。

## 阶段 ⑥ 上报

交付评论汇总各阶段证据与标记：

1. 按六阶段结构汇总，每段带对应标记：`[UNDERSTOOD]` / `[ROOTCAUSE]` / 开发 /
   测试 / 验证 / 上报——证据是原文引用（代码位置、命令输出、测试结果），不是
   形容词。
2. 交付物清单：改动文件列表（路径 + 一句话说明）+ 提交/分支形态。
3. 遗留与边界：没修的、没验证的、需要人工确认的，逐项列明——验收方据此判断
   放行或退回。
4. 不写空头结论：「已修复」必须有 ④⑤ 的证据背书；证据不足的项明确写「待验证」。
